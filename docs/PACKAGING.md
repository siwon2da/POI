# POI 전용 EXE 패키저

POI v1.17부터 Windows 설치본의 `poi build`는 Python, pip, PyInstaller를
호출하지 않는다. 설치된 `poi.exe` 또는 `poi-idle.exe`를 검증된 실행 스텁으로
재사용하고, POI 프로그램을 최적화된 Python 바이트코드로 컴파일해 하나의 EXE에
직접 넣는다. 소스 저장소에서 실행할 때만 개발용 대체 경로로 PyInstaller를 쓴다.

```powershell
poi build app.poi -o app --console
poi verify dist\app.exe
```

## 형식과 실행

앱 코드는 `marshal` 바이트코드로 컴파일하고 zlib 최고 압축률로 압축한다. 압축
페이로드와 JSON 빌드 정보, 고정 길이 푸터를 PyInstaller CArchive 쿠키 바로 앞에
둔다. 쿠키는 계속 파일 끝에 있으며 아카이브 시작 위치도 변하지 않아 기존 POI
부트로더의 실행 호환성을 유지한다. 실행 시 스텁이 컨테이너를 검증하고 POI 런타임
전역, 명령행 인자와 줄 번호 정보를 준비한 다음 앱을 실행한다.

## 안전 장치

- 압축 데이터와 압축 해제된 코드에 각각 SHA-256을 기록하고 실행 전에 검사한다.
- 페이로드는 64MB, 빌드 정보는 64KB로 제한하고 압축 폭탄·잘린 데이터·뒤붙인
  데이터를 거부한다.
- 임시 파일을 완전히 쓰고 디스크에 반영한 뒤 원자적으로 교체해 중간에 실패해도
  반쪽짜리 EXE를 남기지 않는다.
- 경로가 섞인 출력명, Windows 금지 문자와 예약 장치명을 거부한다.
- 빌드 중 셸, pip, 네트워크, 임시 Python 스크립트를 실행하지 않는다.
- 이미 앱이 든 EXE나 현재 실행 중인 스텁 자체를 다시 덮어쓰지 않는다.

SHA-256 검사는 전송·저장 중 손상 탐지용이며 디지털 서명은 아니다. 공격자가 EXE
전체를 바꾸고 해시도 다시 계산할 수 있으므로 배포자의 신원까지 증명하려면 완성
EXE에 별도로 Authenticode 서명을 해야 한다. 스텁에 서명이 있었다면 컨테이너 삽입
후 다시 서명해야 한다.

## 보호 모드

```powershell
poi build app.poi --obfuscate
poi build app.poi --lock "비밀번호"
poi build app.poi --lock "비밀번호" --ask-password --console
```

기본 모드는 원본 POI 텍스트를 넣지 않고 최적화된 바이트코드만 담는다.
`--obfuscate`는 이름과 구조를 한 번 더 흐려 분석 비용을 높인다. 진짜 비밀이 필요한
코드는 `--lock --ask-password`를 사용해야 한다. 이 모드는 PBKDF2로 키를 만들고
인증 암호화를 사용하며 비밀번호를 EXE 안에 저장하지 않는다. 비밀번호를 EXE에
내장하는 `--lock`은 편의 기능이므로 숙련된 분석자에 대한 완전한 보호는 아니다.

## 호환성과 제한

- 결과물은 빌드에 사용한 POI 설치본과 같은 Windows 아키텍처에서 실행된다.
- 표준 라이브러리와 POI 설치본에 포함된 모듈은 바로 쓸 수 있다.
- `use py:`로 부른 외부 패키지가 설치 스텁에 없으면 조용히 누락하지 않고 빌드를
  중단한다. 외부 패키지를 새로 포함해야 할 때는 현재 소스 환경의 PyInstaller
  경로를 사용한다.
- 전용 패키저는 스텁의 아이콘과 Windows PE 버전 리소스를 유지한다. `--author`,
  `--product`, `--file-version` 값은 검증 가능한 컨테이너 빌드 정보에 저장되며,
  `--icon`은 소스/PyInstaller 빌드에서만 PE 아이콘을 바꾼다.
- Python 바이트코드는 스텁의 Python 버전에 묶이지만 앱과 그 스텁을 함께 복사하므로
  대상 PC에 Python을 설치할 필요가 없다.

“100배 안전”처럼 환경에 따라 달라지는 배수는 보장하지 않는다. 대신 위의 각
안전 장치를 테스트로 고정하고, `poi verify`로 결과를 사용자가 직접 확인할 수 있게
한다.
